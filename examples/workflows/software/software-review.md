Review in this Project. Two Steps carry this Skill; the prompt's Step says which. Nobody reviews their own work.

At Design review (a "Design: …" Subtask). Read `docs/design/<PARENT-KEY>.md`, the ADRs, the threat model when there is one, and the slices filed under the Parent (`darkory show <PARENT>`, then each). Check: it meets the Parent's criteria; it is the simplest design that does; the alternatives were real; the slices cover the design, each small and releasable, in an order that works; rollout, rollback and observability are written; every security requirement lands in a slice. End `approved` (the documents merge into the Parent's branch and the slices start) or `redesign` with one line per thing to change.

At Code review (a slice). Read the Task, its criteria, its security requirements and the builder's Note, then the diff (`git diff <base>...HEAD`; the base is in the prompt's Workspaces line), and run the tests yourself. Review on two axes and keep them apart. Spec: it does what the Task says, nothing missing and nothing extra, and a test proves each criterion. Standards: it fits the design document, it is correct at the edges, it is no more complex than it needs, names and comments say what and why, the docs changed with it, and it leaves the code healthier than it found it. Find everything in one pass: run each procedure the change documents (deploy, rotate, roll back) as written, end to end, and keep going after the first finding; a finding held back for the next round costs a whole loop. Write a Note of what you checked on each axis.

End `needs changes` with one line per finding that must change. Otherwise `security review` when the Task carries the `security` Label, or the diff touches authentication, authorisation, secrets or untrusted input, or adds or upgrades a dependency; else `pass`. A suggestion that is optional does not block: put it in the Note and pass.

Always: work only in the checkouts the prompt names, never another path. Run anything that takes over about 90 seconds in the background with its output in a log that ends with its exit status, and read the log at least every 30 seconds until it ends (in Claude Code: `run_in_background`, then a Monitor); never sit silent in one long call. Before you end, record one Observation about the process, not the product: what in this Skill text, the Task as written, or the handover you received helped (`darkory observe <KEY> --worked <text>`) or cost you time (`--didnt-work <text>`).
