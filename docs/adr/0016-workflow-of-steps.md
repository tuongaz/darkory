# A Project's Workflow is Steps and Connectors; a Task's state is its Step

A Project defines one **Workflow**: an ordered set of **Steps**, each named by the Project and carrying at most one Skill, and **Connectors**, each a named outcome out of one Step into another or into Done. An open Task that is not a Parent and is not aimed at a Member is at exactly one Step; the Step's Skill is what `next`, Claim and Takeable read. A Step without a Skill is a hold: no one is offered a Task there, and a human moves it on. The holder ends their work with **advance** `<outcome>`: the Claim ends and the Task waits at the Connector's target Step, or completes when the target is Done. A human may **move** a Task to any Step by hand, and the record says so. Whether a Task is waiting, being worked, or blocked is derived from its Claim and from Blocking and never stored. The Steps carrying the builtin `breakdown`, `acceptance` and `retro` Skills are where Darkory files the Subtasks it owns about a Parent as a whole; a Workflow may have none of them, and such a Project offers no Break down, requires no Acceptance and files no Retrospective. Darkory stores when a Task reached its Step, so the time at each Step is exact.

This supersedes [ADR 0012](0012-tasks-have-a-status.md): there is no Status, no kind, and no move of a Status on Claim or release. It amends [ADR 0001](0001-one-task-moves-through-skills.md): a Task still moves through Skills, but the chain is the Project's Workflow, not the text of each Skill, and Handover is advancing along a Connector.

We chose this because a Task carried three facts for one thing — a Status, the Skill it needed, and its Claim — and Darkory bounced the Status to keep it in sync with the other two (claim → In progress, release → Todo). The Status earned its place only as a column; the Skill said who; the Claim said whether. Reading the Step as the state leaves one fact: a column is a Step, "who" is its Skill, "whether" is the Claim. The owner asked to see a Project's workflow as a flow one can click into — each step a Skill with the agents that hold it, each connector an outcome — and a diagram is only honest when it is the record itself, which Jira's workflow editor shows and a derived-from-Activity picture cannot. With the chain in the Workflow, a Skill text no longer hardcodes `handover --skill qa --status "In QA"`; an accounting Project's Gather → Prepare → Partner review → Lodged is the same mechanism with no agent in it. ADR 0012's objection — that deriving columns from Skills conflates "needs review" with "is being reviewed" — is answered by the Claim staying a separate fact: one column holds both, and the card shows the holder.

Decided on 2026-10-07 with the owner, after two lighter designs were rejected in the same session: Statuses that name a Skill with the list order as the flow, and Statuses with named transitions. Both kept the redundant fact.

## Considered Options

- **Statuses with a Skill each and the list order as the flow.** Visualisable, but a Status that names a Skill is a Step with a second name for its own position.
- **Statuses plus named transitions (Jira).** The canvas the owner wanted, drawn over a Status that still bounced on Claim and release.
- **Observed flow from Activity, no model change.** Honest but blurry: no "what's next" for an empty step, and the chain stays in the Skill texts.
- **Unbounded workflows per kind of Task (Jira schemes).** The layering that made Jira hard to read; a different process is a different Project.
