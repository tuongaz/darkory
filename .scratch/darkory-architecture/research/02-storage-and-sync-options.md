# 02 — Storage and sync options for one shared record of work, reachable from cloud and local

Research date: 2026-10-04. Sources: official docs, repos, release pages, changelogs, issues, and maintainer posts only. Versions and dates are given where read (GitHub releases/commits and npm/crates.io as of 2026-10-04). "Unverified" means I could not confirm the point from a primary source. Evidence about how earlier tools broke (Beads, Backlog.md, Taskmaster, Vibe Kanban, Paperclip) comes from [01-agent-workforce-tools.md](./01-agent-workforce-tools.md) and the primary sources it cites.

## How to read the claim column

Darkory's Claim is exclusive (at most one holder) and never lapses on its own ([CONTEXT.md](../../../CONTEXT.md)). For every option, the question is **where the compare-and-swap (CAS) lives**:

- **A: one authority.** A single process (server, primary or leader) runs a conditional write such as `UPDATE task SET holder=$me WHERE id=$t AND holder IS NULL`, then checks rows-affected. A local claim is at most tentative until the authority acknowledges it.
- **B: merge, no authority.** Replicas accept writes on their own and converge later. Two offline claims both "succeed" locally. On merge, a rule either picks one (last-writer-wins, actor/client-ID order, last push wins) or surfaces a conflict (Dolt cell conflict, git non-fast-forward).
- **C: impossible offline.** A disconnected Member can read but cannot claim.

**The takeable-now query.** As [CONTEXT.md](../../../CONTEXT.md) defines Blocking ("not takeable until every Task blocking it has ended"), the check is one hop deep. In SQL it is a `NOT EXISTS` anti-join over blockers whose Task has not ended, plus `holder IS NULL`, `status = open`, and a skill-or-aimed-at filter. The Handover rule ("cannot take it at the stage they handed it to") adds one more anti-join against handover history. A recursive CTE is only needed for cycle detection or for "why is this blocked" chains. So any engine with real SQL handles the query. Document and CRDT stores without a query layer have to build a client-side index over every Task and blocker edge.

## SQLite: a single file (and a server fronting it)

Verdict: the simplest place for an atomic claim, because SQLite has exactly one writer. It is only safe when every reader and writer is on the same host as the file. To reach it from other machines, SQLite's own docs say to put a proxy process in front.

- **Maturity:** 3.53.4, released 2026-07-24 ([changes](https://www.sqlite.org/changes.html)). Public domain ([copyright](https://www.sqlite.org/copyright.html)).
- **Claim:** A. `BEGIN IMMEDIATE` takes the write lock up front ("might fail with SQLITE_BUSY if another write transaction is already active", [lang_transaction](https://www.sqlite.org/lang_transaction.html)). A conditional `UPDATE … WHERE holder IS NULL` followed by `changes()` ([lang_corefunc](https://www.sqlite.org/lang_corefunc.html)) or `UPDATE … RETURNING` (since 3.35.0, top-level only, [lang_returning](https://www.sqlite.org/lang_returning.html)) is the CAS. `busy_timeout` makes waiting writers sleep and retry ([busy_timeout](https://www.sqlite.org/c3ref/busy_timeout.html)). `BEGIN CONCURRENT` (optimistic page-level locking) is documented only on a branch ([begin_concurrent.md](https://sqlite.org/src/doc/begin-concurrent/doc/begin_concurrent.md)); whether it is in mainline releases is unverified, and the mainline transaction doc lists only DEFERRED/IMMEDIATE/EXCLUSIVE.
- **WAL limits:** "Readers do not block writers and writers do not block readers." "WAL does not work over a network filesystem… processes on separate host machines obviously cannot share memory." "All processes using a database must be on the same host computer" ([wal.html](https://www.sqlite.org/wal.html)).
- **Network filesystems:** "Rely upon it at your (and your customers') peril." SQLite's option 2 is the server-fronting pattern: "Host an SQLite database in WAL mode, but do all reads and writes from processes on the same machine… Implement a proxy that runs on the database machine that relays read/write requests from remote machines" ([useovernet](https://www.sqlite.org/useovernet.html)). Also: "avoid using SQLite in situations where the same database will be accessed directly (without an intervening application server) and simultaneously from many computers over a network" ([whentouse](https://www.sqlite.org/whentouse.html)).
- **Offline:** no replication. A laptop with its own file has a separate record, not a copy of the shared one.
- **New local user:** nothing beyond a bundled driver.
- **Team cloud:** one process owns the file and serves an API. Backups need something extra (see Litestream).
- **Takeable-now:** full SQL. `NOT EXISTS` anti-joins and recursive CTEs ([lang_with](https://www.sqlite.org/lang_with.html)).
- **Failure modes:** broken locking on network filesystems ("especially true of… NFS"), POSIX `close()` cancelling all advisory locks in the process, and two copies of SQLite linked into one app ([howtocorrupt §2.1–2.3](https://www.sqlite.org/howtocorrupt.html)). Write contention shows up as `SQLITE_BUSY`.
- **Seen in 01:** Vibe Kanban started as a local SQLite client and had to move to a server to share boards across a team ([#2812](https://github.com/BloopAI/vibe-kanban/issues/2812)).

## Litestream (backup and read-replica context)

Verdict: disaster recovery for a single-writer SQLite. It adds no claim logic. Its new VFS modes give read-only replicas and an experimental single-writer write mode.

- **Maturity:** v0.5.17 (2026-08-31), last commit 2026-09-21, Apache-2.0, README badge "status-beta" ([repo](https://github.com/benbjohnson/litestream)). v0.5.0 shipped 2025-09-30 after a revamp ([Fly blog](https://fly.io/blog/litestream-v050-is-here/)).
- **What it does:** "a standalone disaster recovery tool for SQLite. It runs as a background process and safely replicates changes incrementally to another file or S3" ([README](https://github.com/benbjohnson/litestream)). WAL mode only ([tips](https://litestream.io/tips/)). The revamp uses S3 conditional writes for a lease so "only one instance of Litestream can replicat[e] to a given destination" ([litestream-revamped](https://fly.io/blog/litestream-revamped/)).
- **Claim:** none of its own. The VFS write mode "assumes a single writer. Multiple concurrent writers will trigger conflict detection", and on conflict "the current sync is aborted and an error is returned" ([vfs-write-mode](https://litestream.io/guides/vfs-write-mode/)). Two claimers would both write locally, and one learns it lost only at sync time.
- **Offline:** VFS read replicas read straight from object storage and poll every 1 s by default, read-only ([vfs guide](https://litestream.io/guides/vfs/)). In write mode, "Uncommitted changes in the buffer since the last sync may be lost on crash".
- **New local user / Team cloud:** one binary plus S3 credentials, as a sidecar to the single app server.
- **Failure modes:** "Writable VFS: FileSize race after sync flush causes 'database disk image is malformed'" ([#1271](https://github.com/benbjohnson/litestream/issues/1271), open). "Database corrupted when restoring from backup" ([#1164](https://github.com/benbjohnson/litestream/issues/1164), open). "VFS writes silently dropped when buffer path not configured" ([#971](https://github.com/benbjohnson/litestream/issues/971), closed). "Multiple applications replicating into the same bucket & path can cause situations where you will be unable to restore" ([tips](https://litestream.io/tips/)).
- Whether 0.3.x removed an earlier read-replica feature is unverified.

## LiteFS (superfly/litefs)

Verdict: single-primary SQLite replication on Linux/FUSE, effectively tied to Fly.io. Fly says it cannot support it, and its last release was April 2025.

- **Maturity:** v0.5.14 (2025-04-22), and the default branch's last commit is the same day. Apache-2.0, README "status-beta" ([repo](https://github.com/superfly/litefs)). Fly docs: "LiteFS is stable and running in production environments. The project is still pre-1.0… We are not able to provide support or guidance for this product. Use with caution" ([docs.fly.io/litefs](https://docs.fly.io/litefs)). LiteFS Cloud: "will continue to be available until October 15, 2024… We're not sunsetting LiteFS itself!" ([community post, 2024-07-15](https://community.fly.io/t/sunsetting-litefs-cloud/20829)).
- **Claim:** A. "Only one node can be the primary at any given time", via a Consul lease. Replication is asynchronous ("A catastrophic crash on the primary would cause these transactions to be lost") ([ARCHITECTURE](https://github.com/superfly/litefs/blob/main/docs/ARCHITECTURE.md)). Writes reach the primary only through the built-in proxy, which uses `fly-replay` and works only on Fly.io ([proxy docs](https://docs.fly.io/litefs/proxy/)).
- **Offline:** replicas are read-only and go stale. Autostop "can result in a stale machine winning the lease and LiteFS discarding newer changes… risking rollback and data loss" ([docs](https://docs.fly.io/litefs)).
- **New local user:** Linux with FUSE. Release assets are Linux only, and macOS FUSE was declined: "we're not going to support FUSE on macOS" ([#119](https://github.com/superfly/litefs/issues/119)).
- **Failure modes:** "LiteFS Panic when WAL is large" ([#445](https://github.com/superfly/litefs/issues/445), open). "SQLITE_CONSTRAINT_CHECK error and rollback stops syncing with other nodes" ([#428](https://github.com/superfly/litefs/issues/428), open).

## rqlite and dqlite (Raft over SQLite, brief)

Verdict: both keep one writer (the Raft leader), so a claim is atomic, but a disconnected node cannot write. rqlite is an easy HTTP server. dqlite is a Linux-only C library.

- **rqlite maturity:** v10.5.1 (2026-10-02), last commit 2026-10-03, MIT ([repo](https://github.com/rqlite/rqlite)).
- **rqlite claim:** A. There are no interactive transactions: "The behavior of rqlite if you explicitly issue BEGIN, COMMIT, ROLLBACK… is not defined". Batches with `?transaction` are all-or-nothing, and each write returns `rows_affected` ([API](https://rqlite.io/docs/api/api/)). So the claim must be one conditional `UPDATE` (RETURNING is supported since v8.23.0 per the [CHANGELOG](https://github.com/rqlite/rqlite/blob/master/CHANGELOG.md)). Writes sent to any node are forwarded to the leader ([FAQ](https://rqlite.io/docs/faq/)).
- **rqlite reads:** levels Weak (default), Linearizable, Strong, None and Auto ([read consistency](https://rqlite.io/docs/api/read-consistency/)). A takeable-now read that must be fresh needs Linearizable or Strong.
- **rqlite local / cloud:** `brew install rqlite` or `docker run rqlite/rqlite` ([install](https://rqlite.io/docs/install-rqlite/)). Single node is fine: "Many people do so, as they like accessing a SQLite database over HTTP" ([FAQ](https://rqlite.io/docs/faq/)). A cluster that loses quorum goes offline (same FAQ). Failure example: "Fast restart can adopt the index of a snapshot that was never restored, thereby hiding committed rows" ([#2747](https://github.com/rqlite/rqlite/issues/2747), closed 2026-08-28).
- **dqlite:** v1.18.7 (2026-07-02), go-dqlite v3.0.4. LGPLv3 with a static-linking exception ([repo](https://github.com/canonical/dqlite)). "dqlite runs on Linux and requires a kernel with support for native async I/O" (README). Cross-platform support is blocked on `mremap` ([#593](https://github.com/canonical/dqlite/issues/593)). "Dqlite transactions can be serialized, however they cannot be linearized", and leader reads can be stale by "a few hundred milliseconds" ([consistency model](https://canonical.com/dqlite/docs/explanation/consistency-model)). Not viable on macOS laptops.

## libSQL and embedded replicas (tursodatabase/libsql)

Verdict: a local SQLite file that reads locally and, by default, sends every write to one remote primary. That makes the claim CAS server-side with read-your-writes. The offline-writes mode is beta and leaves conflicts unresolved. Turso now points new projects at its Rust rewrite.

- **Maturity:** MIT, not archived. Last commit 2026-08-23. Last `libsql-server` (sqld) GitHub release v0.24.32 on 2025-02-14. `@libsql/client` 0.18.0 (2026-09-02) ([repo](https://github.com/tursodatabase/libsql), [npm](https://www.npmjs.com/package/@libsql/client)). README: "libSQL is actively maintained, but new features are being developed in Turso… If you're starting a new project, you probably want to look into Turso" ([README](https://github.com/tursodatabase/libsql)). The Turso README FAQ says the rewrite "replaces libSQL as our intended direction" ([turso FAQ](https://github.com/tursodatabase/turso#faq)).
- **Claim:** A in default mode. "Writes are sent to the remote primary database configured at `syncUrl` by default. They are NOT written to the local file first", and "after a write returns successfully, the replica that initiated the write will always be able to see the new data right away" ([embedded replicas](https://docs.turso.tech/features/embedded-replicas/introduction)). In `offline: true` mode, WAL frames are pushed and the server can answer with a conflict (`InvalidPushFrameConflict`, [sync.rs](https://github.com/tursodatabase/libsql/blob/main/libsql/src/sync.rs)). How the losing client recovers is unverified.
- **Offline:** default mode keeps reads local. That writes fail offline is inferred from "writes are sent to the remote primary". The offline-writes post said: "Conflict detection (but resolution is not yet implemented)", "not yet recommended for production use", "data loss is possible" ([offline sync public beta, 2025-03-31](https://turso.tech/blog/turso-offline-sync-public-beta)).
- **New local user:** a `file:` URL with `@libsql/client` needs no server.
- **Team cloud:** Turso Cloud, or self-hosted `sqld` (Docker). Self-hosted sqld does not support offline writes ([#2037](https://github.com/tursodatabase/libsql/issues/2037), open).
- **Takeable-now:** full SQLite locally.
- **Failure modes:** "Do not open the local database while the embedded replica is syncing. This can lead to data corruption" ([docs](https://docs.turso.tech/features/embedded-replicas/introduction)). "replicator sync | database disk image is malformed" ([#1607](https://github.com/tursodatabase/libsql/issues/1607), open). "Embedded replica sync doesn't work" ([#1900](https://github.com/tursodatabase/libsql/issues/1900), open). Stack overflow on Windows ([#2074](https://github.com/tursodatabase/libsql/issues/2074), open).

## Turso Database and Turso Sync (tursodatabase/turso, formerly Limbo)

Verdict: a Rust rewrite of SQLite with MVCC and a push/pull sync whose default rule, "last push wins", would let a second offline claim overwrite the first. A JS-only transform hook or an experimental remote-writes mode can move the claim back to the server. Pre-1.0, and the company is joining Supabase.

- **Maturity:** v0.8.1 (2026-09-29), v0.8.2-pre.2 (2026-10-02), MIT ([releases](https://github.com/tursodatabase/turso/releases)). FAQ: "Turso powers production applications today… we have not yet reached 1.0… some features are explicitly marked experimental… we recommend… keep independent backups" ([FAQ](https://github.com/tursodatabase/turso#faq)). Turso Cloud: "Turso databases on Turso Cloud are in early preview" ([turso-cloud](https://docs.turso.tech/turso-cloud)). Turso's sync post (2026-04-24): "you should be using Turso, not libSQL, if you are using sync", but "our docs and official communications still recommend libSQL (for now)" ([sync-benchmark](https://turso.tech/blog/sync-benchmark)).
- **Ownership change:** "Turso is joining Supabase" (2026-10-02). "The Turso platform continues… Your databases, APIs, and workflows continue as they do today." "Open source stays open. Turso Database remains open source and actively developed" ([turso blog](https://turso.tech/blog/turso-is-joining-supabase)). The post says nothing about libSQL or sync.
- **Claim (local):** MVCC `BEGIN CONCURRENT`: "If two transactions modify the same data, one will receive a conflict error and must roll back and retry" ([concurrent-writes](https://docs.turso.tech/tursodb/concurrent-writes)). That gives a real CAS between processes on one file.
- **Claim (across replicas):** B by default. "Logical statements are sent, and on conflicts the strategy is 'last push wins'" ([sync usage](https://docs.turso.tech/sync/usage)). On pull with unpushed changes, the local DB "is rolled back to the last synced state", remote changes are applied, and local changes are "replayed on top" ([conflict resolution](https://docs.turso.tech/sync/conflict-resolution)). The JS `transform` hook can `keep`, `skip` or `rewrite` each mutation before it is pushed (same page). The repo's test rewrites to `value = value + ?` ([promise.test.ts](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/sync/packages/wasm/promise.test.ts)), so a claim could be rewritten to a conditional update, which moves it towards A. The Rust SDK hardcodes `use_transform: false` ([rsapi.rs](https://github.com/tursodatabase/turso/blob/main/sync/sdk-kit/src/rsapi.rs)). How a losing client learns it lost, other than seeing the winner's row after a pull, is unverified. `remoteWritesExperimental` (JS) sends writes to the remote, which is A.
- **Offline:** "write locally and call `push()` when the connection is available. All changes are safely stored in the local database file until they can be synced" ([sync usage](https://docs.turso.tech/sync/usage)).
- **New local user:** `npm i @tursodatabase/database`, `cargo add turso`, `pip install pyturso`, or the `tursodb` CLI.
- **Team cloud:** Turso Cloud (free tier: 100 DBs, 5 GB, 3 GB syncs/month, [pricing](https://turso.tech/pricing)). `tursodb --sync-server` exists, but the docs frame it "for development and testing without Turso Cloud" with no auth ([local sync server](https://docs.turso.tech/sync/local-sync-server)). A production self-hosted sync server is unverified.
- **Takeable-now:** SQLite dialect, but compatibility is "not at 100% yet" ([COMPAT.md](https://github.com/tursodatabase/turso/blob/main/COMPAT.md)). Recursive CTE support is unverified (the one-hop anti-join does not need it).
- **Failure modes:** "Lost Updates Under Concurrent Read-Modify-Write" ([#5421](https://github.com/tursodatabase/turso/issues/5421), closed 2026-02). "MVCC passive checkpoint can alias a stale table ID to an index root, causing data loss" ([#7960](https://github.com/tursodatabase/turso/issues/7960), open). "Sync pull fails when replay reassigns an existing STRICT INTEGER PRIMARY KEY" ([#9330](https://github.com/tursodatabase/turso/issues/9330), open). 900 open issues.

## cr-sqlite (vlcn-io/cr-sqlite), and SQLite Sync and Corrosion

Verdict: SQLite tables as CRDTs, with column-level last-writer-wins. Two offline claims both commit, and the merge silently keeps one. Upstream has been effectively unmaintained since 2024.

- **Maturity:** last release v0.16.3 (2024-01-17). Commits stopped from 2024-10 to 2026-08; the recent ones are community build fixes ([repo](https://github.com/vlcn-io/cr-sqlite)). Maintainer (2024-12-30): "I'm full time on https://zero.rocicorp.dev/ these days… I don't see that happening for at least 1-2 years" ([#444 "Is this project dead?"](https://github.com/vlcn-io/cr-sqlite/issues/444)). Fly maintains a fork ([superfly/cr-sqlite](https://github.com/superfly/cr-sqlite)).
- **Claim:** B. "Rows are maps of CRDTs… Columns can be counter, fractional index or last write wins CRDTs" ([README](https://github.com/vlcn-io/cr-sqlite)). The merge rule (as documented by Corrosion): "Biggest `col_version` wins", then the "biggest" value, then site_id ([Corrosion CRDTs](https://superfly.github.io/corrosion/crdts.html)). The losing holder is overwritten with no signal. CRR tables cannot have unique indices other than the primary key, nor checked foreign keys ([tableinfo.rs](https://github.com/vlcn-io/cr-sqlite/blob/main/core/rs/core/src/tableinfo.rs)).
- **Offline / local / cloud:** full local reads and writes. Load the extension and call `crsql_as_crr('tasks')`. Changes exchange via `crsql_changes` ([docs](https://vlcn.io/docs/cr-sqlite/api-methods/crsql_changes)). You build and host the relay yourself.
- **Failure modes:** "`DROP TABLE` leads to corruption?" ([#433](https://github.com/vlcn-io/cr-sqlite/issues/433)). "Duplicate `seq` for the same `db_version`" ([#380](https://github.com/vlcn-io/cr-sqlite/issues/380)).
- **SQLite Sync (sqliteai/sqlite-sync):** 1.2.0 (2026-09-28). CRDT ("Standard CRDT sync replaces an entire cell when two devices edit the same column"), so B. It syncs to SQLite Cloud, PostgreSQL or Supabase and is pitched "For AI agents". License: "Elastic License 2.0 (modified for open-source use)", and a commercial license is required to replace the network layer ([LICENSE](https://github.com/sqliteai/sqlite-sync/blob/main/LICENSE.md)). Open issue: concurrent Postgres transactions "can take the same db_version, and a download then skips one of them" ([#79](https://github.com/sqliteai/sqlite-sync/issues/79)).
- **Corrosion (superfly/corrosion):** v1.0.0 (2026-05-14), Apache-2.0. Gossip over the cr-sqlite fork, so the same LWW (B). It targets server clusters, and "writes to the database all have to go through Corrosion" ([docs](https://superfly.github.io/corrosion/crdts.html)).

## Postgres: server or managed

Verdict: the textbook home for an exclusive claim and a takeable-now query. Laptop Members must be online to claim. Local zero-setup is the cost.

- **Maturity:** PG 18 (18.6 current; 18.0 released 2025-09-25, supported to 2030-11-14). PG 19 Beta 4 came out 2026-09-24 ([versioning](https://www.postgresql.org/support/versioning/)). PostgreSQL License ([licence](https://www.postgresql.org/about/licence/)).
- **Claim:** A. In Read Committed, a concurrent updater "will wait for the first updating transaction to commit or roll back… The search condition of the command (the WHERE clause) is re-evaluated" ([transaction-iso](https://www.postgresql.org/docs/current/transaction-iso.html)). So `UPDATE … WHERE holder IS NULL RETURNING *` has at most one winner. `FOR UPDATE SKIP LOCKED` "can be used to avoid lock contention with multiple consumers accessing a queue-like table" but "provides an inconsistent view of the data" ([SELECT](https://www.postgresql.org/docs/current/sql-select.html)). Row locks end with the transaction, so a claim that never lapses has to be a stored column, not a held lock (inference).
- **Offline:** C for any Member that cannot reach the server.
- **New local user:** a Postgres server (see PGlite and embedded Postgres below for local paths).
- **Team cloud:** managed or self-hosted. Neon is "joining forces with Databricks" ([2025-05-14](https://neon.com/blog/neon-and-databricks)). Neon free: 100 projects, "100 CU-hours/project", "1 GB/project, 20 GB account total", scale-to-zero after 5 min that "cannot be turned off" ([pricing](https://neon.com/pricing)). Supabase free: 2 active projects, 500 MB, "paused after 1 week of inactivity" ([pricing](https://supabase.com/pricing)).
- **Takeable-now:** the best fit in this sample. Anti-joins, recursive CTEs with a `CYCLE` clause ([queries-with](https://www.postgresql.org/docs/current/queries-with.html)), and partial indexes on `holder IS NULL`.
- **Seen in 01:** Paperclip runs one Postgres (embedded locally or hosted) behind a Node server and avoids sync altogether. Its bugs are in lock lifecycle, not storage ([execution-semantics](https://github.com/paperclipai/paperclip/blob/master/doc/execution-semantics.md)).

## PGlite (electric-sql/pglite)

Verdict: real Postgres SQL in a ~3.7 MB WASM package with no install. It is single-connection, has no sync, and corrupts its data directory if two processes open it.

- **Maturity:** v0.5.8 (2026-08-26). Apache-2.0 / PostgreSQL License ([repo](https://github.com/electric-sql/pglite)). It runs in the browser, Node, Bun and Deno, with filesystem, IndexedDB or memory storage (README). The fork's default branch is `REL_18_3-pglite`, which suggests a PG 18.3 base (inferred, [postgres-pglite](https://github.com/electric-sql/postgres-pglite)).
- **Claim:** A, but only inside one process: "PGlite is single user/connection" ([README](https://github.com/electric-sql/pglite)). Browser tabs elect a leader that "handles all queries" ([multi-tab worker](https://pglite.dev/docs/multi-tab-worker)). Several OS processes (several agent CLIs on one laptop) are not covered: two processes on the same `dataDir` "both succeed, both write, and the directory ends up unreadable" ([#1106](https://github.com/electric-sql/pglite/issues/1106), open).
- **Sharing over the wire:** `@electric-sql/pglite-socket` provides a `pglite-server` CLI with a connection multiplexer, but "not all use cases are guaranteed to work", and "SSL connections are NOT supported" ([pglite-socket](https://github.com/electric-sql/pglite/tree/main/packages/pglite-socket)). `pg-gateway`'s last npm publish was 0.3.0-beta.4 (2024-12-23) ([repo](https://github.com/supabase-community/pg-gateway)).
- **Offline / cloud:** fully local, but a separate record. There is no built-in link to a team Postgres.
- **Failure modes:** "pglite-socket: concurrent extended-protocol batches interleave across connections; one internal throw permanently deadlocks the query queue" ([#1046](https://github.com/electric-sql/pglite/issues/1046)). "close() racing an in-flight statement wedges PGlite permanently" ([#1084](https://github.com/electric-sql/pglite/issues/1084)). "QueryQueueManager deadlocks when handler disconnects mid-transaction" ([#985](https://github.com/electric-sql/pglite/issues/985)).

## Embedded native Postgres (npm `embedded-postgres`, zonky)

Verdict: a real multi-connection Postgres started by your process. Paperclip uses it for local mode. It costs a 25–55 MB download and a child server whose lifecycle you manage.

- **Maturity:** npm `embedded-postgres` 18.4.0-beta.17 (2026-06-05), MIT. Per-platform binaries for darwin arm64/x64, linux (several archs) and windows-x64 ([repo](https://github.com/leinelissen/embedded-postgres)). Measured tarballs: about 55 MB on darwin-arm64 and about 24 MB on linux-x64. It "requires post-install scripts to function" (README). Java alternative: zonky embedded-postgres v2.2.2 (2026-03-01), Apache-2.0 ([repo](https://github.com/zonkyio/embedded-postgres)).
- **Claim:** A, with full Postgres semantics across local processes.
- **Offline / cloud:** a separate local record unless one Postgres is made the authority and the others connect to it.
- **Failure modes:** "initialise() and start() promises may never settle when subprocesses stall" ([#34](https://github.com/leinelissen/embedded-postgres/issues/34)). "stop() never resolves if the postmaster already exited" ([#32](https://github.com/leinelissen/embedded-postgres/issues/32)). Paperclip patches out the library's exit hooks, which "must not be allowed to stop a cluster independently" ([paperclip repo](https://github.com/paperclipai/paperclip)).

## Dolt (dolthub/dolt)

Verdict: a SQL database with git-style branches, push and pull. One `sql-server` gives an atomic claim. Across clones, two offline claims become a cell conflict that someone has to resolve after the fact. Beads lived through this storage in 2026 (see 01).

- **Maturity:** v2.4.1 (2026-10-02), Apache-2.0, about 41–44 MB per platform ([release](https://github.com/dolthub/dolt/releases/tag/v2.4.1)). `dolt sql-server` speaks the MySQL protocol. Embedding is Go only ([dolthub/driver](https://github.com/dolthub/driver)).
- **Claim within one server:** A. "One writer is allowed to commit their transaction and the other is rolled back" ([transactions](https://www.dolthub.com/docs/concepts/dolt/sql/transaction)). "Dolt does not implement SELECT FOR UPDATE because this is the default behavior" ([blog 2023-12-14](https://www.dolthub.com/blog/2023-12-14-concurrent-transaction-example/)).
- **Claim across clones:** B with an explicit conflict. "If two operations modify the same row, column pair to be different values, a conflict is detected" ([conflicts](https://www.dolthub.com/docs/concepts/dolt/git/conflicts)). Conflicts land in `dolt_conflicts_<table>`, and Dolt "will automatically rollback any transaction with merge conflicts when you attempt to COMMIT it" ([merges](https://www.dolthub.com/docs/sql-reference/version-control/merges)). `dolt push` rejects non-fast-forward updates unless `--force`, which overwrites "any conflicting history in the remote" ([CLI](https://www.dolthub.com/docs/cli-reference/cli)). So the first pusher wins, and the second sees the double claim as a `holder` conflict at pull time.
- **New local user:** a ~41 MB binary.
- **Team cloud:** a shared `dolt sql-server`, or DoltHub/DoltLab as the remote.
- **Takeable-now:** SQL with CTEs. A recent bug hit exactly that shape: "panic… in mergeJoinIter.removeParentRow with recursive CTE + NOT EXISTS" ([#10472](https://github.com/dolthub/dolt/issues/10472), closed).
- **Seen in 01 (Beads on Dolt):** embedded and server mode flipped back and forth several times between 2026-01 and 2026-04. Per-clone `UUID()` keys made "`bd dolt pull` fail unrecoverably" ([#4259](https://github.com/gastownhall/beads/issues/4259)). Independent schema migrations "fork the schema and break `bd dolt pull`" ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)). Cross-clone claim races are unverified there.

## Git-backed files (Markdown or JSONL in a repo)

Verdict: zero install beyond git and readable by anyone. The only atomic primitive is the remote's ref update, so the git host becomes the claim authority. There is no query engine, and merges either conflict or keep both claims.

- **Claim:** A, with the remote as authority. "Only fast-forward updates are allowed" on branches. `--force-with-lease=<ref>:<expect>` requires "its current value to be the same as the specified value", and `--atomic` means "Either all refs are updated… or no refs are updated" ([git-push](https://git-scm.com/docs/git-push)). Locally, `git update-ref` updates "only if its current value is <old-oid>" ([git-update-ref](https://git-scm.com/docs/git-update-ref)). On GitHub, `PATCH /repos/{owner}/{repo}/git/refs/{ref}` with `force=false` will "make sure you're not overwriting work", failing with 422 ([refs API](https://docs.github.com/en/rest/git/refs)). Every claim is therefore a commit plus a push round trip.
- **Offline → reconnect:** commits are tentative. A rejected push forces fetch and rebase. With `merge=union`, git will "take lines from both versions… Do not use this if you do not understand the implications" ([gitattributes](https://git-scm.com/docs/gitattributes)). For a JSONL claim line, that would keep both holders (inference).
- **New local user:** git. **Team cloud:** a git host. GitHub limits: 5,000 requests/hour authenticated, and secondary limits of "80 content-generating requests per minute" and "500… per hour" ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)).
- **Takeable-now:** no engine. Every client parses every file. Backlog.md derives readiness "from the whole visible corpus at read time" ([CLI-INSTRUCTIONS](https://github.com/MrLesk/Backlog.md/blob/main/CLI-INSTRUCTIONS.md)).
- **Seen in 01:**
  - Backlog.md: six concurrent self-assigns, "all 6 exit 0… 1 assignee survives" ([#843](https://github.com/MrLesk/Backlog.md/issues/843)). Sequential IDs "cannot be made safe" across machines ([#711](https://github.com/MrLesk/Backlog.md/issues/711)).
  - Taskmaster: "conflict armageddon in git", and the owner's answer that "the value of a centralized database (ideally remote) is huge" ([#88](https://github.com/eyaltoledano/claude-task-master/issues/88)).
  - Beads deleted its JSONL-in-git sync (~7.6k lines) for Dolt ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)).

## Replicache (rocicorp)

Verdict: the original optimistic-mutation, server-authoritative sync engine. It is now in maintenance mode and its repo is archived, with users pointed to Zero.

- **Status:** "Replicache is now in maintenance mode… We have open-sourced the code and no longer charge for its use… We will continue to support Replicache, but won't add new features" ([replicache.dev](https://replicache.dev/)). The GitHub repo was "archived by the owner on Jun 10, 2026" ([repo](https://github.com/rocicorp/replicache)). npm 15.3.0 (2025-07-02). The npm license field still points to "https://roci.dev/terms.html"; the open-source license terms are unverified.
- **Claim:** A, in your push endpoint. The client "rewinds the state… to the last version it got from the server, applies the patch… and then replays any pending mutations" ([how it works](https://doc.replicache.dev/concepts/how-it-works)). For an invalid mutation, the server "must still mark the mutation as processed by updating the lastMutationID" ([server-push](https://doc.replicache.dev/reference/server-push)). So a rejected claim silently vanishes on the next pull, with no error callback (inference from the two quotes).
- **Offline:** mutations queue and replay on reconnect.
- **Local / cloud:** bring your own backend and storage. **Takeable-now:** a client key-value store, so you build the index yourself.

## Zero (rocicorp, zero.rocicorp.dev)

Verdict: Postgres-backed sync with server-run mutators, client-side revert on rejection, and a query language that can express "no un-ended blockers". It deliberately refuses offline writes.

- **Maturity:** "As of March 2026, Zero is generally available and fully-supported" ([status](https://zero.rocicorp.dev/docs/status)). npm `@rocicorp/zero` 1.9.0 (2026-08-14), Apache-2.0, daily canaries. GitHub issues are disabled; the tracker is bugs.rocicorp.dev.
- **Architecture:** "It replicates Postgres into a SQLite replica inside `zero-cache`, then syncs subsets of rows to clients" via logical replication ([llms.txt](https://zero.rocicorp.dev/llms.txt)).
- **Claim:** A. Mutators "run on the client optimistically first", then `zero-cache` calls your `ZERO_MUTATE_URL`, "where they run directly against Postgres". On server error, "The optimistic mutation on the client will be reverted", and the client can await `.server` and see `type === 'error'` ([mutators](https://zero.rocicorp.dev/docs/mutators)).
- **Offline:** C. "Zero does not support offline writes." When disconnected, "writes are rejected and return an offline error". The rationale given: "Custom business logic and authorization rules can pass while offline, but break when the user reconnects" ([offline](https://zero.rocicorp.dev/docs/offline)).
- **New local user:** Postgres with `wal_level=logical`, `npx zero-cache-dev`, and your app server ([install](https://zero.rocicorp.dev/docs/install)). Official support for non-browser (Node agent) clients is unverified; there is a `zero-sqlite3` package for Node/Bun ([repo](https://github.com/rocicorp/zero-sqlite3)).
- **Team cloud:** self-host one zero-cache, or multi-node (replication-manager plus view-syncers, with Litestream backup to S3) ([self-host](https://zero.rocicorp.dev/docs/self-host)). "Cloud Zero" is described as "fully managed by the Zero team" ([cloud-zero](https://zero.rocicorp.dev/docs/cloud-zero)); public availability is listed as a 2026 roadmap item, so unverified.
- **Takeable-now:** ZQL supports `exists` with `not`, so `not(exists('blockers', …))` expresses it ([ZQL](https://zero.rocicorp.dev/docs/zql)). There are no aggregates yet. Client reads only see synced rows.

## Electric (electric-sql/electric)

Verdict: read-path sync from Postgres into clients. Writes, and therefore the claim, go through your own API. Electric is repositioning around agents.

- **Maturity:** `@core/sync-service` 1.8.1 (2026-09-07), `@electric-sql/client` 1.5.28, Apache-2.0. The repo is now titled "The agent platform built on sync" ([repo](https://github.com/electric-sql/electric), [electric.ax](https://electric.ax/)).
- **Claim:** A, built by you. "Electric does read-path sync… Electric does not do write-path sync" ([writes guide](https://electric.ax/docs/guides/writes)). With TanStack DB, "If the handler throws an error, the optimistic state is rolled back" ([TanStack DB](https://tanstack.com/db/latest/docs/overview)). TanStack DB is pre-1.0 (0.11.3). Electric's own baseline for rejected writes: "clear all local state if any write is rejected" ([writes guide](https://electric.ax/docs/guides/writes)).
- **Offline:** reads come from cache. Writes follow whatever pattern you choose.
- **New local user:** Postgres (logical replication), the Electric container, and your write API. The client is plain HTTP and works from Node.
- **Team cloud:** Electric Cloud ("fully managed… usage-based pricing") or self-hosting the Elixir service.
- **Takeable-now:** "Shapes are currently single table, though you can use subqueries to filter based on related data. Shape definitions are immutable" ([shapes](https://electric.ax/docs/guides/shapes)). A per-skill takeable shape with a `NOT IN (subquery)` is possible; the join happens locally.
- **Failure modes:** "TRUNCATE unpublishes the table; writes made before the next shape re-publishes it are silently lost forever" ([#4773](https://github.com/electric-sql/electric/issues/4773), closed 2026-09). "Subquery-based shape fails to sync DELETE when CASCADE removes the join-table rows" ([#4004](https://github.com/electric-sql/electric/issues/4004)).
- **Seen in 01:** Vibe Kanban's remote crate used Postgres plus Electric, and the remote side was removed at its sunset ([crates/remote](https://github.com/BloopAI/vibe-kanban/tree/main/crates/remote), [shutdown](https://www.vibekanban.com/blog/shutdown)).

## PowerSync

Verdict: a client-side SQLite synced from Postgres, Mongo or MySQL, plus an offline upload queue to your backend. That backend is the claim authority, but a rejection must be returned as success and signalled some other way.

- **Maturity:** powersync-service v1.26.1 (2026-09-11), licensed FSL-1.1-ALv2 ([LICENSE](https://github.com/powersync-ja/powersync-service)). SDKs are Apache-2.0. "Node.js SDK | GA", "Sync Streams | GA", "Open Edition | GA" ([feature status](https://docs.powersync.com/resources/feature-status)). Sync Streams support JOINs, CTEs and subqueries ([changelog May 2026](https://powersync.com/blog/powersync-changelog-may-2026)).
- **Claim:** A, through your backend. "The SDK places every write to the SQLite database in an upload queue and uploads the queue to your backend" ([Node SDK](https://docs.powersync.com/client-sdks/reference/node)). If the next checkpoint lacks the write, "local data gets removed" ([writing client changes](https://docs.powersync.com/handling-writes/writing-client-changes)). "Your backend should return 2xx for validation errors or write conflicts"; a 4xx "will block the PowerSync client's upload queue" ([client-side integration](https://docs.powersync.com/configuration/app-backend/client-side-integration)). A losing claim is overwritten at the next checkpoint unless you sync an explicit rejection (inference).
- **Offline:** "If the device is offline, writes accumulate in the upload queue and are uploaded automatically when connectivity is restored."
- **New local user:** the PowerSync Service, source Postgres with logical replication, bucket storage (MongoDB or Postgres), and your API ([local development](https://docs.powersync.com/tools/local-development)). No local-only mode is documented.
- **Team cloud:** PowerSync Cloud, or self-hosted Open Edition (Docker, at least 512 MB, plus a MongoDB replica set) ([deployment architecture](https://docs.powersync.com/maintenance-ops/self-hosting/deployment-architecture)).
- **Takeable-now:** full SQL on the client SQLite, as fresh as the last checkpoint.
- **Failure modes:** "Postgres storage returns a bucket's operations twice… (client checksum failure loop)" ([service #813](https://github.com/powersync-ja/powersync-service/issues/813)). "Upload queue not performing correctly" ([js #605](https://github.com/powersync-ja/powersync-js/issues/605), open).

## InstantDB

Verdict: a hosted or self-hostable triple store on Postgres with optimistic client transactions. It has no conditional-write primitive, so an exclusive claim would rest on a permission rule whose race-safety is unconfirmed.

- **Maturity:** `@instantdb/core` 1.0.67 (2026-08-31), Apache-2.0. "A sync server written in Clojure talks to Postgres… we store all user data as triples in one big Postgres database" ([repo](https://github.com/instantdb/instant)). The self-host VPS route bundles "backend, dashboard, PostgreSQL, MinIO, and Caddy" ([self-hosting](https://instantdb.com/docs/self-hosting.md)).
- **Claim:** A-ish. "If the server returns a failure, we simply remove the change from the pending queue" ([architecture essay](https://www.instantdb.com/essays/architecture)). Transactions are all-or-nothing ([instaml](https://instantdb.com/docs/instaml.md)), but there is no compare-and-set. A permission rule can compare `data` (pre-state) with `newData` ([permissions](https://instantdb.com/docs/permissions.md)). Whether that check runs atomically against committed state under concurrency is unverified.
- **Offline:** a persistent pending queue (IndexedDB or AsyncStorage), flushed on reconnect.
- **New local user:** Instant Cloud, or docker compose (Postgres plus a JVM server). There is no embedded mode. Python is admin-SDK only ([start-python](https://instantdb.com/docs/start-python.md)).
- **Takeable-now:** InstaQL supports links, `$isNull`, `$ne` and `$in`. No documented anti-join over links ([instaql](https://instantdb.com/docs/instaql.md)).
- **Failure modes:** "Update as upsert does not work as expected on deleted rows" ([#2769](https://github.com/instantdb/instant/issues/2769), open). "`data.ref` rules don't use optimistic attrs" ([#232](https://github.com/instantdb/instant/issues/232)).

## Convex (other serious option found)

Verdict: a reactive backend whose server mutations are serializable, the strongest claim guarantee among the sync engines here. It also has an account-free local backend (beta). There is no local SQL replica; queries run on the server.

- **Maturity:** backend FSL-1.1-Apache-2.0 with daily builds (latest 2026-10-02) ([convex-backend](https://github.com/get-convex/convex-backend)). npm `convex` 1.46.0.
- **Claim:** A. "Provides true serializability and will yield correct results regardless of what transactions are issued concurrently", with conflicts retried automatically ([OCC](https://docs.convex.dev/database/advanced/occ)). Optimistic updates are "rolled back when a mutation completes" ([optimistic updates](https://docs.convex.dev/client/react/optimistic-updates)).
- **Offline:** mutations are queued in memory while disconnected. `ConvexHttpClient` queues by default since 1.25.0 ([CHANGELOG](https://github.com/get-convex/convex-js/blob/main/CHANGELOG.md)). Persistence across restarts is unverified.
- **New local user:** "develop with Convex without having to create an account". The backend runs as a subprocess of `npx convex dev`. Beta ([local deployments](https://docs.convex.dev/cli/local-deployments)).
- **Team cloud:** Convex Cloud, or self-host. Self-host uses "By default… local SQLite", with Postgres or MySQL optional, and "supports all the free-tier features of the cloud-hosted product" ([self-hosted README](https://github.com/get-convex/convex-backend/blob/main/self-hosted/README.md)). Clients exist for JS/TS, Python and Rust ([self-hosting](https://docs.convex.dev/self-hosting)).
- **Takeable-now:** arbitrary TypeScript query functions on the server.
- **Failure mode:** "setAuth during reauthentication after an AuthError leaves the WebSocket stopped permanently" ([convex-js #194](https://github.com/get-convex/convex-js/issues/194)).

## Automerge

Verdict: a mature JSON CRDT that merges without coordination. Two concurrent claims both succeed, and the merge picks a winner deterministically. Exclusivity is only possible by routing claims through a server you write. There is no query layer.

- **Maturity:** `@automerge/automerge` 3.5.0 (2026-09-16), MIT. Automerge 3 cut memory use by "around a 10x reduction" ([repo](https://github.com/automerge/automerge)). `automerge-repo` npm `latest` is 2.6.0-alpha.3 ([releases](https://github.com/automerge/automerge-repo/releases)); its current stable line is unverified. Python: `pip install automerge` ([automerge-py](https://github.com/automerge/automerge-py)).
- **Claim:** B. "Automerge picks one of the concurrently written values as the 'winner', and it ensures that this winner is the same on all nodes… Conflicts are ordered based on the counter first (using the actorId only to break ties)". The others are "relegated to a conflicts object" ([conflicts](https://automerge.org/docs/reference/documents/conflicts/)). Keyhive (access control, "pre-alpha… DO NOT use… in production") is not an invariant authority ([keyhive](https://github.com/inkandswitch/keyhive)).
- **Offline:** full offline editing. The concurrent claim loses silently on merge.
- **New local user:** npm plus `storage-nodefs`, with no server for single-machine use.
- **Team cloud:** `automerge-repo-sync-server` (v0.3.0, 2026-09-30), "an unsecured Express app", so add your own auth ([README](https://github.com/automerge/automerge-repo-sync-server)).
- **Takeable-now:** "A document is the 'unit of change'" ([concepts](https://automerge.org/docs/reference/concepts/)). You load Task documents and build the index on the client.
- **Failure modes:** "High memory spike on load and save operations sometimes causes out of memory" ([#705](https://github.com/automerge/automerge/issues/705), open). "Out of memory errors after creating enough large documents in repo" ([automerge-repo #330](https://github.com/automerge/automerge-repo/issues/330), open). "Sync server scalability for live collaboration" ([#207](https://github.com/automerge/automerge-repo/issues/207), open).

## Yjs

Verdict: the most widely used CRDT for collaborative editing. Concurrent map writes resolve by an implementation detail (client ID order). Server-side rejection only exists as "drop the connection".

- **Maturity:** 13.6.33 (2026-09-23), with v14.0.0-rc.28 (2026-09-29). MIT ([LICENSE](https://github.com/yjs/yjs/blob/main/LICENSE)). Ports: yrs (Rust) and pycrdt (Python, 0.14.8); ypy is archived ([pycrdt](https://github.com/y-crdt/pycrdt)).
- **Claim:** B. The docs only say types "automatically merge without merge conflicts" ([docs](https://docs.yjs.dev/)). In the source, concurrent items are ordered by client ID and the right-most becomes the map value ([Item.js v13.6.33](https://github.com/yjs/yjs/blob/v13.6.33/src/structs/Item.js)). In practice the higher (random) clientID wins, as observed by a user on the [forum](https://discuss.yjs.dev/t/y-map-conflict-resolution-which-side-wins/1952) and not confirmed by the maintainer. Hocuspocus `beforeHandleMessage` can reject, but "If you throw an error in the hook, the connection will be closed" ([hooks](https://tiptap.dev/docs/hocuspocus/server/hooks)).
- **Offline / local / cloud:** offline editing with `y-indexeddb`. Servers: y-websocket (3.1.0), Hocuspocus (4.7.0, "sqlite persistence, webhooks, auth"), or y-sweet ([README](https://github.com/yjs/yjs)).
- **Takeable-now:** no query layer, so a client index.
- **Failure modes:** "document object continuously growing with 'deleted' items" ([#493](https://github.com/yjs/yjs/issues/493)). "How to implement validation / disaster recovery?" ([hocuspocus #135](https://github.com/ueberdosis/hocuspocus/issues/135)).

## Jazz 2.0 (garden-co/jazz)

Verdict: a local-first relational database that adds a server "fate authority" for exclusive, first-committer-wins transactions. That is the only CRDT-lineage engine here with a built-in exclusive claim. It is an alpha rewrite.

- **Maturity:** "Jazz 2.0 alpha with an entirely new API", v2.0.0-alpha.58 (2026-09-30), MIT, Rust core ([repo](https://github.com/garden-co/jazz)). The CoValues codebase moved to [classic-jazz](https://github.com/garden-co/classic-jazz) (`jazz-tools@0.20.19`, 2026-07-03).
- **Claim:** A. "Exclusive write validation MUST be first-committer-wins" ([SPEC 3_transactions](https://github.com/garden-co/jazz/blob/main/crates/jazz/SPEC/3_transactions.md)). "The authority checks the reads and writes, then accepts or rejects the transaction as one serialisable unit." On rejection, `wait()` "rejects with PersistedWriteRejectedError and Jazz removes the rejected local changes" ([transactions](https://jazz.tools/docs/writing/transactions)). Caveat: "The authority checks only the reads the writing client reports". It is "not a security boundary" (same page).
- **Offline:** exclusive transactions "can be staged, but cannot be accepted until the authority is reachable". Unsynced local commits "MAY be lost if local storage is destroyed" (SPEC INV-TX-12).
- **New local user:** `npm create jazz`. A Node backend uses `jazz-tools@alpha jazz-napi@alpha` with an app ID and server URL ([TS server](https://jazz.tools/docs/install/typescript-server)). No Python is documented (unverified).
- **Team cloud:** Jazz Cloud ("Unclaimed apps auto-delete after 14 days") or `npx jazz-tools@alpha server` self-hosted ([server setup](https://jazz.tools/docs/getting-started/server-setup)). Pricing unverified.
- **Takeable-now:** relational `where`/`include` queries read from local storage ([queries](https://jazz.tools/docs/reading/queries)). Anti-join support is unverified.
- **Failure modes:** "Browser query coverage can stall under concurrent CI load" ([#2413](https://github.com/garden-co/jazz/issues/2413)). Classic: "nodejs worker doesn't re-sync upon reconnection to sync server" ([classic-jazz #1373](https://github.com/garden-co/classic-jazz/issues/1373), closed).

## Patterns that cut across options (observations, not recommendations)

1. **Every option that keeps "at most one holder" puts the CAS in one place.** The local-first engines that preserve exclusivity (Zero, PowerSync, Electric + API, Replicache, Convex, Jazz 2.0 exclusive tx, libSQL default; InstantDB only if its permission-rule check is atomic, which is unverified) all run the claim on a server and treat the local write as tentative. The engines that let a claim commit offline (Automerge, Yjs, Loro, cr-sqlite, Turso Sync default) settle a double claim after the fact, either by a fixed rule or by surfacing a conflict.
2. **"Offline claim" splits into three behaviours:** refuse it (Zero: "Zero does not support offline writes"; Jazz: "cannot be accepted until the authority is reachable"), queue it and reverse it later (PowerSync, Replicache, Instant, Convex in memory), or accept it and merge (CRDTs, Turso Sync). Zero's stated reason, that business rules "can pass while offline, but break when the user reconnects", describes the same class of failure as the check-then-act claims Beads shipped in 01 (there a same-DB race, not an offline one).
3. **How a client learns its claim lost varies a lot:** an explicit error (Zero `.server`, Jazz `PersistedWriteRejectedError`, Convex mutation error), silent disappearance (Replicache on next pull, PowerSync at next checkpoint with a forced 2xx), a conflict object (Automerge `getConflicts`, Dolt `dolt_conflicts_*`), or nothing at all (cr-sqlite, Yjs).
4. **"Local-first" means three different shapes in this sample:** (a) a local process that *is* the record (SQLite file, PGlite, embedded PG, Dolt, `npx convex dev`); (b) a local cache of a cloud record (libSQL replicas, Zero, PowerSync, Electric); (c) a full replica that merges (CRDTs, Turso Sync, Dolt clones, git). Only (b) and (c) give laptop and cloud Members the same record without one of them connecting to the other's process. Shape (a) gives zero setup only for a single machine.
5. **Zero setup and one shared record pull against each other.** The zero-install options (SQLite, PGlite, git, CRDT libraries) either have no sharing or rely on merge. The options with a server-side claim usually need Postgres with logical replication plus a sync service plus an API (Zero, Electric, PowerSync). The exceptions are client libraries pointed at a hosted endpoint (libSQL/Turso, Jazz Cloud, Instant Cloud, Convex Cloud), which trade setup for a vendor dependency. Vibe Kanban's forced move from local SQLite to a server, and its users' complaints about self-hosting, are the cost seen in 01 ([#2812](https://github.com/BloopAI/vibe-kanban/issues/2812), [#3354](https://github.com/BloopAI/vibe-kanban/issues/3354)).
6. **Single-process local stores break under several local agent processes.** PGlite is "single user/connection" and corrupts a shared `dataDir` (#1106). Embedded replicas warn against opening the file during sync. SQLite needs everyone on one host and serialises writers. Every single-process local store in this sample assumes one process per data directory; the case of several agent CLIs on one laptop is not covered by their docs.
7. **The one-hop takeable query is easy in any SQL engine** and only discriminates against document and CRDT stores. What differs among SQL options is freshness: the authority's copy (Postgres, rqlite Strong reads) versus a synced subset (PowerSync checkpoint, Zero/Electric shapes, embedded replica `syncInterval`). A Member can see a Task as takeable on a stale copy, and the authority's CAS then rejects the claim.
8. **"Claims never lapse" removes TTLs from storage requirements but not reversal.** No option needs leases. Every option still needs a "taken back" write that overrides the CAS, and in merge-based options that override is itself subject to the merge rule.
9. **Churn in this layer is high.** In the last 18 months: Replicache archived, cr-sqlite paused, Triplit acquired and idle, LiteFS Cloud sunset, libSQL deprioritised, Turso acquired, Jazz rewritten as 2.0 alpha, Beads' storage rewritten several times (01). Of the sync engines here, Zero (GA March 2026) and PowerSync (GA components) state a stable status; Electric is 1.x but I found no status label either way.
