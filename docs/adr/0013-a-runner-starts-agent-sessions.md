# A runner starts agent sessions, pulling through `next`

A Local Install runs a **Runner** beside the Tracker. For each agent Member with agent settings, the Runner loops on `next` as that Member; when it claims a Task it prepares a **Workspace** (a directory with one checkout per Workspace the Task names — a git worktree on a branch named after the Task), writes a prompt from the record (the Skill's current text, the Task and its Feature, the Notes, the Evidence, the working rules and the exit rules), and starts the agent's **command** — Claude Code by default, with the agent's model — inside a tmux session named after the Task, with the Darkory MCP server attached. The agent ends the Task itself, through MCP: Complete, Hand over, or a question that blocks it. The Runner never completes a Task on an agent's behalf; when the Claim ends it exits the session and attaches the session log as Evidence. A turn that ends with the Claim still held is nudged twice, then released with a Note.

Heartbeats are the Runner's, and they are **gated on progress**: Claude Code's transcript file for the session (the Runner chooses the session id) changed within two minutes means a Heartbeat; stale means none, and the Claim lapses on the Tracker's own rule. No hook, no time budget: a hung session lapses the way a dead one does, and a long session that keeps working is never cut off. (Amended 2026-10-08, model v2's M3: a long tool call writes nothing until it returns, and MAIN-1's builders lapsed inside a silent ten-minute `make verify`, so a quiet transcript is not yet stale while a process the session started after its last record is running, and, failing that, while its last record is a tool call in flight, for up to the Claim's own timeout; a call that hangs with no process of it running still lets the Claim lapse.) Sessions run with Claude Code's permission checks skipped; the worktree and the exit rules are the fence. One session per agent at a time. (Amended 2026-10-10, the dogfood follow-ups: an agent's settings say how many Shifts the Runner runs for it at once, `shifts`, 1 unless set; each Shift still works under its own Session holding its own Claim, so one Session per Claim stands, and the run of 2026-10-10 showed why a ceiling of one serialises a Project: with one builder, two Tasks at Fix are already a queue.) A human watches or joins a session from the web through a terminal bridged to `tmux attach` (admins may type; others read), or from a shell with `darkory attach`.

We chose this because the human asked for a Local Install where "start the app, file a Feature, and agents pick it up and complete it", and the Tracker by design never starts an agent ([ADR 0005](0005-http-canonical-with-long-poll-claim.md)): something has to. Putting that something beside the server, pulling through the same `next` every external agent uses, keeps every rule of the record in one place — the Runner is a client, not a second scheduler — and makes `darkory agents` on another machine the same program with a token. tmux was chosen over a headless transcript relay because it gives the real session, watchable and joinable, for free on the machine that runs it; the web terminal is a window onto it. The transcript's modified time was chosen over hooks because, on a Local Install, the Runner knows where every session's file is and a file time cannot be forgotten by a model the way a hook call can.

Decided on 2026-10-07; the question-by-question record is in `docs/build/agents-plan.md`.

## Considered Options

- **Headless sessions (`claude -p`) with a relay for watching and typing.** Exits on its own and produces a structured transcript, but the relay is a new path through the server, the view is a rendering rather than the session, and a worker machine would need the server to proxy both ways.
- **Always-on agent loops** (each session calling `next` itself, for hours). Closest to the test bots, but a session that lives for hours drifts and carries context it no longer needs; one session per Claim keeps each prompt fresh.
- **The Runner completes the Task when the command exits 0.** Simpler, but "it ran" would count as "it is done", which is the distinction Claim and Complete exist to keep.
- **Hooks for Heartbeats** (a Heartbeat on every tool call, a signal on every turn end). Exact, but another thing to install and keep in step with the agent runtime; the transcript file carries both facts already.
- **An allowlist of permitted tools** with prompts surfaced as Escalations. Safer and still available per agent later; a prompt that nobody sees stalls an unattended session, so skipping permissions is the default the human chose for now.
