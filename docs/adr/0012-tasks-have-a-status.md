# Tasks have a Status the Organisation defines

A Task carries a **Status** chosen from a list the Organisation defines and orders: by default Backlog, Todo, In progress, In review, Done and Dropped. Every Status is of one of five **kinds** — backlog, todo, in_progress, done, dropped — and the rules read the kind, never the name. A Task in a backlog-kind Status is not takeable, so `next` never offers it: people decide what agents may pull. Done- and dropped-kind Statuses are reached only by Complete and Drop, and a Task never leaves them. Claimed and blocked stay what they were: facts derived from the Claim and from Blocking, whatever the Status.

Darkory moves the Status on its own acts, so an agent working through `next` needs no second call: a Claim moves a todo-kind Task to the first in_progress-kind Status; Complete moves it to the first done-kind, Drop to the first dropped-kind; a Claim that ends any other way — release, lapse, take-back, a revoked token, a closed Session, a deactivated Member — returns an in_progress-kind Task to the first todo-kind Status, so a Task nobody holds never reads as in progress. Hand over leaves the Status unless the holder names one. Any Member of the Feature's Team may move a Task between the open kinds (backlog, todo, in_progress) by naming the Status; naming a done- or dropped-kind Status is refused, because those are Complete and Drop. The list is one per Organisation, and a change that would leave it without a todo, in_progress, done or dropped kind, or that would delete a Status Tasks are in without saying where they go, is refused.

We chose this because the web app's board view, decided on 2026-10-06 to follow Linear, drags cards between columns, and the record had nothing to drag: a Task was open, done or dropped, with claimed and blocked derived ([ADR 0004](0004-sqlite-local-postgres-cloud.md)). A column that is not a field is a status invented by the screen. The human asked for user-defined Statuses such as Backlog, Todo and In review, and the same request answers a second need: before this, every open Task was takeable the moment it was filed, so a planner could not file work ahead of the Team without agents pulling it.

The Status is stored on the Task and the Takeable rule reads its kind in the same SQL fragment as before, so `claim`, `next` and `takeable` keep one rule and one statement ([ADR 0004](0004-sqlite-local-postgres-cloud.md)); the moves on Claim, Complete and Drop are made inside the same conditional UPDATE, so the hot paths keep their one round trip ([ADR 0011](0011-organisation-writes-run-one-at-a-time.md)). The in_progress kind stays takeable so that a lapsed Claim, which leaves its Task in progress until the lapse is recorded, can be taken again at once.

Recorded on 2026-10-07, from the UI redesign board and its three decisions (D1 what moves a Status, D2 one list per Organisation, D3 who moves a card), taken as drawn.

## Considered Options

- **Derived columns only (Waiting · Blocked · Claimed · Done).** No model change, but nothing to drag, no Backlog, and a board that cannot show "In review" without reading the Skill a Task needs, which conflates "needs review" with "is being reviewed".
- **A Status that only people set, as in Linear.** Simpler rules, but an agent's `next` would leave its card in Todo while it works, and every agent would need a second call to say "in progress"; the board would be wrong by default.
- **One Status list per Team.** Linear's shape; deferred. The Takeable rule is Organisation-wide and Members cross Teams, so one list is enough for now and per-Team lists can be added without changing the screens.
