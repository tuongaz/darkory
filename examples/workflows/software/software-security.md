Security in this Project. Two Steps carry this Skill; the prompt's Step says which. Never fix code yourself.

At Threat model (a "Design: …" Subtask). Read `docs/design/<PARENT-KEY>.md` and the ADRs on this branch, the Parent's criteria and the code it touches. Answer the four questions. What are we working on: the actors, entry points, trust boundaries and assets, in words. What can go wrong: STRIDE at each entry point. What are we going to do about it: a mitigation for each threat, or an accepted risk with its reason. Did we do a good enough job. Write `docs/security/<PARENT-KEY>-threat-model.md` on this branch and commit it, ending with numbered Security requirements (SR-1 …), each checkable by a test or in review. Add each requirement as a Note to the slices it binds (`darkory note <slice> "SR-2: …"`) and Label them `security` (setting Labels replaces the whole set: pass the Labels a slice already has too). After a redesign, diff from your last threat-model commit and record only the delta. End `accepted` when every high threat has a mitigation in the design or a requirement; `redesign` with a Note of what the design must change when a threat cannot be mitigated without changing it.

At Security review (a slice). Read the diff against its base (`git diff <base>...HEAD`; the base is in the prompt's Workspaces line), the threat model and the requirements bound to the Task. Check: authentication and authorisation on every new path; input validated, output encoded; secrets never in code, tests, logs, history or the image (`git log -p <base>..HEAD` searched for keys, tokens, passwords); secrets compared in constant time and stored hashed when they are verified rather than used; errors that leak nothing; limits on sizes, time and rate; each new dependency needed, maintained, pinned and free of known vulnerabilities (`govulncheck ./...`, `npm audit` or the ecosystem's equivalent; say so when none can run). Run each tool with the toolchain version the project pins (its module or build file), never whatever is installed, and name the version that ran it. Attach the review as Evidence (`security-review-<KEY>.md`: each finding with severity high, medium or low, what and where, and each requirement met or not) and write a Note summarising it. A finding that breaks one of the Task's criteria or a bound requirement is at least medium. End `pass` when no high or medium finding is open (put the low ones in the Note); `needs changes` with one line per finding to fix.

Always: work only in the checkouts the prompt names, never another path. Run anything that takes over about 90 seconds in the background with its output in a log that ends with its exit status, and read the log at least every 30 seconds until it ends (in Claude Code: `run_in_background`, then a Monitor); never sit silent in one long call. Before you end, record one Observation about the process, not the product: what in this Skill text, the Task as written, or the handover you received helped (`darkory observe <KEY> --worked <text>`) or cost you time (`--didnt-work <text>`).
