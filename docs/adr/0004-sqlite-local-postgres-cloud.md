# SQLite on Local, Postgres on Cloud: one portable schema, one conditional claim

A self-hosted install stores the record in SQLite by default, inside the single binary, and can be set to use Postgres instead. Cloud stores it in Postgres. Both engines share one schema, one set of migrations and one set of queries, and every rule must behave the same on both.

- **Claim.** A claim is one conditional `UPDATE … WHERE … RETURNING`. The `WHERE` holds every takeable check: open; unclaimed or lapsed; aimed at the Member, or needing a Skill the Member has and belonging to a Feature in one of the Member's Teams; no unfinished blocker; no self-review. The one exception to the Skill check is the Feature owner's fallback for a Retrospective ([ADR 0010](0010-retrospectives-observations-skill-versions.md)). One row back wins. No row means an explicit "already claimed" error, and the loser stops instead of retrying. `next` picks a Task and claims it in the same way, and relies on [ADR 0011](0011-organisation-writes-run-one-at-a-time.md) to find the next takeable Task when another caller wins the first. One race test suite runs against both engines.
- **Claims and states.** A Task stores only open, done or dropped. "Claimed" is derived from the Claim, so it cannot go stale when a Claim lapses. The Task row carries the current Claim, and every Claim also leaves a row of its own, written in the same transaction: holder, Session, Skill, Skill version, model label if the Member sent one, start, end, and how it ended. The Skill version of a Claim and the no-self-review check read those rows, never Activity.
- **Heartbeat lapse.** Computed at read time from `claim_expires_at`, so correctness needs no background job. A heartbeat is a conditional update scoped to the holder. If it returns no row, the Member has lost the Claim. The claiming `UPDATE` copies the outgoing holder into a column, because `RETURNING` gives only the new values on SQLite and gives the old ones only from Postgres 18. The next claimer writes the lapse record from that column, and a sweeper writes it for visibility only. Take-back is a conditional update by the Reporting line or the Feature owner.
- **Takeable now.** Computed at read time and never stored. Blocking is an edge table, and a recursive CTE refuses cycles when an edge is added.
- **IDs.** A UUIDv7 internal ID, plus a per-Team display key such as `WEB-42` that the server allocates in the creating transaction.
- **Evidence.** Metadata in the database. Files go behind a blob-store interface: local disk by default, or S3-compatible storage when the install is set to use it, as Cloud is.
- **Tenancy.** An `org_id` on every row, and every query filters by it. Cloud adds Postgres row-level security as a second lock; those policies live in the private repo ([ADR 0009](0009-agpl-core-closed-cloud-operations.md)).
- **History.** Current-state tables are the source of truth. Each change appends an Activity row in the same transaction, numbered from the Organisation's counter ([ADR 0011](0011-organisation-writes-run-one-at-a-time.md)).

We picked SQLite for Local because it needs nothing installed. We picked Postgres for Cloud for its managed operations and multi-tenancy. The cost is two engines. Keeping every rule in portable SQL, and running each Organisation's writes one at a time ([ADR 0011](0011-organisation-writes-run-one-at-a-time.md)), contains that cost: no engine-specific locking, no stored flags that can go stale (Beads' `is_blocked`), and no reaper that correctness depends on (Paperclip's leaked locks).

Revised 2026-10-05 by the [independent architecture review](../../.scratch/darkory-architecture/issues/13-independent-architecture-review.md). The first text held each rule to a single statement and left writes concurrent on Postgres; experiments showed three rules then behave differently on the two engines, which ADR 0011 settles. The review also made storage a setting of the install instead of a property of Local, moved the row-level security policies to the private repo, replaced the stored "claimed" state with a derived one, gave every Claim a row of its own, added the Team condition to the claim, and said how the lapse record learns the outgoing holder.

## Considered Options

- **SQLite everywhere, one file per Organisation.** One engine and physical isolation, but less standard Cloud operations.
- **Postgres everywhere: through Docker, started by the binary (embedded Postgres), or PGlite on Local.** One engine. But Docker breaks zero setup; embedded Postgres is a heavier Local with a child process to manage and no Windows arm64 build; PGlite is pre-1.0 and tied to a JS runtime. Raised again in the 2026-10-05 review and declined again: zero setup is a reason to build, and SQLite can be dropped later far more cheaply than it can be added.
- **Explicit locks or version-number concurrency.** Engine-specific code or retry loops. Check-then-act let several Members win the same claim in Beads.
- **A stored takeable flag; a reaper for lapses.** Both are known failure modes in the survey.
- **A schema or database per Organisation in Cloud.** Stronger isolation, but migrations and pooling per tenant.
- **Event sourcing.** A full trail, but claims would run against a projection.
