# A Project has one or more named Workflows; a Task's Workflow is that of its Step

A Project's Steps and Connectors are grouped into one or more **Workflows**, each named by the Project, each drawn on a canvas of its own and shown as the columns of its own board. A Step belongs to exactly one Workflow, and Step names stay unique across the Project. A Connector leads out of a Step into a Step of the same Workflow, into a Step of another Workflow of the same Project, or into Done. A Task's Workflow is that of the Step it is at, read and never stored: a Task still has no kind, and it changes Workflow only by advancing along a crossing Connector or by a move, both of which the record shows. A Parent and a Task aimed at a Member have no Step; where they are listed is read from their Subtasks and from the Task they block, by the same rule the board uses, so every reader places a Task alike. Takeable, `next`, Claim and Handover read the Step's Skill as before. A filed Task's default entry Step and the Steps carrying the builtin `breakdown`, `acceptance` and `retro` Skills stay one each per Project across its Workflows, each the first in the order the Consequences give. Rank stays one per Project, across its Workflows.

This amends [ADR 0016](0016-workflow-of-steps.md): "one Workflow per Project" becomes one graph per Project, in named Workflows. Everything else in it stands: the Step is the state, there is no Status and no kind, the Claim is a separate fact, and a Connector is the outcome the holder names. Its rejection of Jira's workflow schemes stands too, stated precisely: what was rejected is a Workflow chosen by a Task's kind; what is adopted is a Workflow read from the Task's Step.

We chose this because one Project's work has flows that share Skills but not Steps: bugs, features, UI prototypes that are never released, support. The core has never required Steps to connect, so these were already islands on one canvas, but a board shows every Step as a column, and the software Workflow alone has fourteen. The owner asked to see the bug flow alone, and a prototype flow apart from the one that releases. A bug flow one can look at alone cannot share a Build column with features, or "bugs only" is a filter again; a View cannot be the answer, because a View is one Member's own, so there would be no shared Support board. Naming the islands gives each its board, its canvas and its lead time with no new fact on the Task. Step names unique per Project are what keep each board unambiguous, where Jira's Statuses shared across schemes did not. One Rank across Workflows keeps the honest order: a bug ranked above a feature is taken first. A prototype's Done lands in its own Workspace, so finishing one deploys nothing. The same Members serve every Workflow, because Takeable reads the Skill of the Step. The router that sends a Task into one Workflow or another is a Step with a Skill, Triage, whose agent advances along a crossing Connector: the Tracker still starts nothing, and the route has an author and a Skill version.

Decided on 2026-10-09 with the owner, after separating two readings of "several Workflows per Project": a Workflow assigned to the Task by a router, which puts a second fact on the Task that drifts from its Step, rejected; and a Workflow read from the Step, adopted.

## Considered Options

- **One Workflow per Project with islands, and board Views per Member.** Already expressible, but a View is one Member's own, so there is no shared Support board, and the editor draws every Step at once.
- **A Workflow chosen by the Task's kind, at filing or by a router (Jira's schemes).** A second fact on the Task; refused by ADR 0016 and again here.
- **Shared Steps across Workflows: one Build column for bugs and features.** Fewer Steps, but a flow cannot be seen alone, which was the ask.
- **One Project per flow: Bugs, Features, Prototypes as Projects.** Splits the key sequence, the Members and the Rank of one body of work, which ADR 0015 made a Project.

## Consequences

- The write stays the Project's whole graph: `PUT …/workflow` carries the Workflows and every Step with its Workflow, so a crossing Connector and the Step it reaches land in one write. The editor edits one Workflow at a time and saves whole; the board reads one at a time, and `workflow show` reads one, or all under a heading each. A Project's existing Steps and Connectors become its one Workflow, named Work, and Step ids keep Tasks in flight where they are.
- A Workflow has a position, and a Project's Steps are ordered by Workflow position, then Step position: "the first Step" (a filed Task's default entry) and the first Step carrying each of `breakdown`, `acceptance` and `retro` read that order, so they keep their meaning with no new fact.
- An ended Task keeps the Step it ended at (`last_step_id`), so its card lands on the board of the Workflow it ended in; the Task is still at no Step.
- A Connector into another Workflow's Step is drawn on both canvases: as an exit naming its target on the one it leaves, as an entry on the one it reaches.
- Which Workflow a board opens on and how the switcher reads are decisions for the build, recorded in `docs/build/decisions.md`.
- A new Project starts with three Workflows (2026-10-10, the owner's call pending): Implementation (Backlog · Plan · Build · Review), Bug triage, and Retrospective (Retro · Skill review), so the Steps a Parent's end files work at are their own Workflow and Implementation ends on its line; an existing Project keeps its Workflows.
