# Ids are written short at the API's boundary; storage keeps UUIDs

Every id in Darkory is a UUID (UUIDv7 from `store.NewID`, which every record, built-in Skills and Organisations included, is made with). People see it in its **short form**: 22 characters of base58 in the Bitcoin alphabet, the UUID's 128 bits as one number, left-padded with `1` (the alphabet's zero), such as `1CTuJUrXDEC71Dv55PHKrq` for `0199c2a0-7b3e-7c41-9f12-842120d6a1b2`. 58^22 is the first power of 58 above 2^128, so every UUID has exactly one short form and every short form one UUID. The alphabet is in ASCII order and the width is fixed, so short ids sort byte for byte as their UUIDs do and UUIDv7 ids still sort by creation time (a property test proves it). `internal/shortid` is the codec and `web/src/lib/shortid.ts` its twin; both read `api/shortid-vectors.json`.

The change is at the boundary only. Storage keeps the canonical 36-character text on both engines, and the server converts on the way out and in:

- **Out.** Every id in a response is short: the spec marks each one `format: id` (the `ID` schema gives its pattern), and the server's generated types map that format to `shortid.ID`, which writes itself short. A spec test fails when a property named as an id lacks the format. Free-form maps — Activity payloads, on the list and the stream, and an Error's `details`, and the ids its message names — are rewritten by one walk in `convert.go`: every string spelled as a UUID, at any depth and as a map key, except under the keys that hold what a person typed or a program was told (`title`, `name`, `body`, `env`, …). A View's saved filters are written with short ids.
- **In, both forms, forever.** `shortid.ID` reads either form in a path, a query parameter and a body; the core's resolvers take `id = canonical OR name = as given`, its by-id getters, Workflow and Label references and filter values canonicalise; the `Darkory-Session` header is canonicalised before the Session is found or started. An old link, the CLI's stored Session, a Runner's kept files and any 36-character id in the owner's notes keep working. A name may be spelled as neither form, so a reference by id or name stays unambiguous.
- **Edges that need a UUID keep one.** Claude Code's `--session-id` and the transcript it writes (`<session>.jsonl`): the Runner renders `{session_id}` and finds the transcript by the canonical text. The blob store's keys (`<org>/<id>`, whose disk store allows lower case only) are built from canonical ids. The Runner's `sessions/<KEY>` folders, branches, worktrees and tmux names are made from display keys, not ids. The Runner's kept logs written before this carry a long Member id and are compared by canonical text.
- **Not ids.** Task display keys (`SAM-12`), secrets (tokens, login-link codes, the cookie) and Idempotency-Keys are untouched. A Session's id is the one its running copy chose: written short when it is a UUID, unchanged otherwise. A browser Session is now known by its own id (it was `browser-<UUID>`), so it shows short too.

We chose this because the owner wanted every id shown whole, with Copy, and a whole UUID is 36 characters that the web app had been cutting to "…842120d6". 22 characters fit on one line at a phone's width in a Sessions table; the fixed width keeps columns steady and the order is the creation order the UUIDs already had.

Storage is not changed because the owner's Install holds real data and the change is reversible only if nothing stored depends on it: Postgres and SQLite columns, foreign keys, Activity payloads, View filters, idempotency replays and the blob store all keep the form they have, and dropping short ids would be a change to the boundary alone. A retry that spells an id differently from the first request is `idempotency_key_reused` (the request's hash is of its bytes), which is right, since a retry resends the same bytes; a reply kept under an Idempotency-Key before the change replays with long ids for its 24 hours.

Decided on 2026-10-08 by the owner ("Use short UUID instead of full ID for all UUIDs") and the lead.

## Considered Options

- **Store short ids.** A migration of every table, payload and blob key on the owner's Install, irreversible in practice, for no gain: the database never shows an id to a person.
- **Rewrite every UUID-shaped string in every response.** One choke point, but it would rewrite a title or an environment variable that happens to be a UUID; typed fields plus a keyed walk of the free-form maps are exact.
- **Type the Go client too.** The client is Apache-2.0 so that a program can import it without license questions (ADR 0009); it would then import the AGPL codec. It passes ids through as the API wrote them, which is all a client needs.
- **Base62 or Crockford base32.** Base32 is 26 characters; base62 keeps `0`/`O` and `l`/`I`, which read alike in a monospace font. Base58 is the shortest alphabet without them that sorts in ASCII order.
- **Truncate the shown id (the last 8 characters).** What the web did; it hid the id the owner needed to copy and compare.
