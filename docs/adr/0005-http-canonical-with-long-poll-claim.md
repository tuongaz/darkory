# HTTP is the canonical agent contract, with a long-poll claim

Agent Members reach Darkory through one HTTP+JSON API, defined spec-first in `openapi.yaml` and versioned in the path (`/v1`, additive changes only; a breaking change ships as `/v2` beside it). The CLI and the MCP server are thin clients written on the Go client generated from that spec, and live in the same `darkory` binary that runs the Local server. Future connectors (events, gRPC) are adapters beside HTTP, not replacements. Humans use the same operations: Members are symmetric. Every request carries the Member's token and the id of the Session making it ([ADR 0008](0008-members-act-through-sessions.md)); the CLI takes that id from `DARKORY_SESSION`, and `darkory prime` prints a fresh one.

An idle agent learns of new work by long-polling `next`, which holds the request open until a Task becomes takeable for that Member and claims it in the same step. It offers Tasks in Rank order. Across a Member's Teams it compares Rank positions, so a Feature ranked first in any Team comes before one ranked second in any Team, and a tie goes to the Task that has waited longest since it was filed or last handed over. Within a Feature, Tasks that block another Task come first, so that questions are answered before new work starts, and then the Task that has waited longest. `next` and `claim` give the Claim a heartbeat timeout: the one the call names, or else the default stored on the token. `darkory mcp` sends Heartbeats for its Session's Claims for as long as it runs, and the CLI has a background heartbeat command for agents that work between calls. This is how Temporal workers poll task queues: still pull, never a push that starts an agent, and no race between seeing work and claiming it. Every write carries an idempotency key so a retry after a lost reply returns the original result instead of claiming a second Task or filing a duplicate.

Revised 2026-10-05 by the [independent architecture review](../../.scratch/darkory-architecture/issues/13-independent-architecture-review.md). The CLI and MCP server were first described as generated from the spec; the generator produces Go server stubs, clients and types, so they are written by hand on the generated client. The Session id, the token's default timeout and the Heartbeat senders are new: a Task claimed through `next` had no timeout, and nothing said who sends Heartbeats while an agent works. The order in which `next` offers Tasks was settled the same day.

## Considered Options

- **CLI canonical.** Fast for local agents, but on Local it tempts writing straight to the database file, which breaks one authority per Organisation and the identical Local/Cloud interface; non-shell callers have nothing to call.
- **MCP canonical.** Good inside agent harnesses, but ties the contract to one protocol's lifecycle, fits long-held Claims poorly, and humans and scripts would still need HTTP.
- **gRPC canonical.** Streaming heartbeats fit well, but it is unreachable from curl and browsers and needs generated clients in every sandbox. Kept as a possible later connector.
- **Short polling, SSE, or webhooks to agents.** Polling is wasteful and slow; SSE separates "work exists" from claiming and races; webhooks need a public agent URL and edge toward Darkory starting agents.
- **The caller names the Team, or oldest first within a Feature.** The first leaves the choice between Teams to each agent; the second lets a question wait behind older Tasks.
